## 5. Recommended Discovery Strategy

### Step 1: Work by version-group cohort, not by single replay

Do not start with one isolated replay unless the cohort is too small.

Current recommended first cohort:

- `16.6`

Reason:

- it has the largest recent replay cohort in the repo
- corpus support is better than `16.5`
- latest-patch family behavior is more valuable than proving one legacy replay

Good secondary cohorts after that:

- `16.1`
- `15.23`
- `15.22`

### Step 2: Use current cleaned artifacts, not legacy one-off JSON

The prototype script [prototype-cleaned-correlation-health.mjs](/C:/Development/league-replay-analyzer/scripts/prototype-cleaned-correlation-health.mjs) is useful as a sketch only.

The real discovery path should read:

- `artifacts/<replay-id>/families/<family-key>/cleaned.json`
- `artifacts/<replay-id>/summary.json`
- `replays/api/<match-id>/timeline.json`

The next script to build should be an artifact-driven cohort scanner, for example:

- `scripts/discover_scalar_metric_candidates.mjs`

Expected inputs:

- `--artifact-root`
- `--version-group`
- `--metric health`

Expected outputs:

- ranked candidate list across the cohort
- grouped support by `versionGroup + familyKey + offset + decode`
- grouped support by broader family-band alias where needed

### Step 3: Start with health

Recommended order:

1. `health`
2. `power`
3. `healthMax`
4. `powerMax`
5. `movementSpeed`

Why:

- `health` and `power` are volatile enough to be distinctive
- `healthMax` and `powerMax` are easier to confuse with other bounded values
- `movementSpeed` may be the noisiest and most buff-sensitive

### Step 4: Use metric-specific validators

Do not score these metrics like `level` or `xp`.

Recommended validator shape:

- `health`
  - non-monotonic
  - bounded
  - large fight-window drops
  - death-window collapse behavior
- `power`
  - non-monotonic
  - bounded
  - role/champion dependent
  - often sawtooth-like around spell usage
- `healthMax`
  - mostly piecewise stable
  - changes with items, levels, temporary buffs
- `powerMax`
  - mostly piecewise stable
  - may be zero or missing for some champions
- `movementSpeed`
  - bounded
  - non-monotonic
  - should not behave like position, gold, or xp

Minimum useful filters:

- overlap threshold
- bounded-range plausibility
- volatility score
- correlation threshold
- normalized RMSE threshold
- anti-confusion penalty when a candidate also matches `gold/xp/cs`

### Step 5: Promote only cross-replay candidates

Do not treat a single replay correlation hit as a schema.

A candidate should only be considered real when:

- it recurs in multiple replays from the same version group
- it keeps the same family and offset semantics, or a clearly clustered family-band alias
- it survives participant assignment without depending on one participant only
- it does not get outcompeted by a sibling decode of the same raw window

### Step 6: Feed winners into the existing schema path

The schema flow should remain:

1. discover candidates from artifacts
2. rank and aggregate them replay-locally
3. aggregate them corpus-wide
4. extract replay-only stats
5. validate against Riot fixtures

Do not hand-maintain a patch-offset table unless we later decide to create a stable schema registry after repeated proof.

## 6. Concrete Next Implementation

Build a new script:

- `scripts/discover_scalar_metric_candidates.mjs`

Responsibilities:

- load replay artifacts for a chosen version group
- load fixture scalar series for one target metric
- scan cleaned fields across the cohort
- compare candidate raw windows to the target metric
- score candidates with metric-specific rules
- emit:
  - `artifacts/scalar-metric-discovery/<version-group>/<metric>.json`
  - grouped support by exact family+offset+decode
  - grouped support by family band when exact families drift

Suggested first run:

```powershell
node .\scripts\discover_scalar_metric_candidates.mjs --artifact-root .\artifacts --version-group 16.6 --metric health
```

## 8. Success Criteria

This task is successful when:

1. at least one of `health`, `power`, `healthMax`, `powerMax`, or `movementSpeed` is discovered through the artifact-driven cohort workflow
2. that metric is promoted through the current schema pipeline rather than a one-off hardcoded offset
3. rerunning the full corpus pipeline populates replay-only extracted values for that metric on at least some replays
4. those extracted values validate without breaking the current `level/xp/totalGold/minionsKilled` results
